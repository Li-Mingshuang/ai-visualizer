Transformer 注意力机制

Jagged Full Attention
不规则全注意力

当一个 batch 里有不同长度的序列时，传统 padding 方案浪费大量计算。Jagged Attention 把序列紧凑打包，让注意力只在每条序列内部计算，消除无效计算。

1  问题：变长序列的 Padding 浪费

Transformer 的注意力计算要求同一个 batch 里的序列等长。最简单的做法是对短序列补 padding token，使所有序列和最长的那条一样长。

但 padding token 是无意义的——它们不携带信息，却占用了大量计算资源。当序列长度差异很大时，浪费尤为严重。

问题可视化 · Padding 浪费

灰色格子 = Padding token（无意义计算）；彩色格子 = 真实 token。
序列长度差异越大，浪费越严重。

有效 token：— Padding token：— 计算浪费：—
极端情况：如果 batch 里有一条长序列（1000 token）和三条短序列（10 token），padding 后有效计算只占 25%，75% 都浪费在 padding 上。

2  解法：序列打包（Packing）

Jagged Full Attention 的核心思路是：把所有序列首尾相接地拼在一起，形成一条长序列，但在计算注意力时，每个 token 只能看到同一原始序列内的 token。

拼接后的序列长度 = 所有原始序列的长度之和，没有任何 padding，计算利用率达到 100%。

对比 · Padding vs Packing

上方 = Padding 方案（补齐到最大长度）；下方 = Packing 方案（紧凑拼接）。相同颜色 = 同一原始序列。

关键问题是：打包后如何让每个 token 只关注自己所在序列的 token？答案是通过不规则注意力掩码（Jagged Mask）。

3  核心：不规则注意力掩码

注意力掩码决定了哪些位置对可以互相 attend。在打包后的序列上，合法的 attend 关系只存在于同一原始序列内部——这形成了块对角（Block Diagonal）结构。

不同于正方形的完整矩阵，各块大小不同，边界参差不齐，这就是 "Jagged"（锯齿状）名称的来源。

交互 · 注意力掩码形状
Padding 方案

每个序列看到补齐后的完整行，包括 padding 位置（深灰 = 被 mask 的 padding）

Jagged 方案

块对角结构，每个序列只看自己的 token，无 padding 浪费，边界呈锯齿状

悬停格子查看 attend 关系

这种掩码结构决定了注意力矩阵 $\mathbf{A}$ 是块对角的：

$$\mathbf{A} = \begin{pmatrix} \mathbf{A}_1 & \mathbf{0} & \mathbf{0} & \mathbf{0} \\ \mathbf{0} & \mathbf{A}_2 & \mathbf{0} & \mathbf{0} \\ \mathbf{0} & \mathbf{0} & \mathbf{A}_3 & \mathbf{0} \\ \mathbf{0} & \mathbf{0} & \mathbf{0} & \mathbf{A}_4 \end{pmatrix}$$
$\mathbf{A}_i$ = 第 $i$ 条序列内部的注意力矩阵（大小为 $l_i \times l_i$）；块外全为 0（不 attend）

4  因果 vs 非因果 Jagged

根据任务类型，每个对角块内部可以是全注意力或因果注意力：

非因果（双向）

用于 BERT 类编码器。每条序列内，每个 token 可以看到序列中所有其他 token（包括后面的）。每个块是一个完整正方形。

场景：文本分类、句子嵌入

因果（单向）

用于 GPT 类解码器。每个 token 只能看到序列中它之前的 token。每个块是一个下三角形。

场景：语言模型预训练、文本生成

对比 · 非因果 vs 因果 Jagged 掩码
非因果（Bidirectional）

块内全填充，序列内每个 token 互相可见

因果（Causal）

块内下三角，只能看到过去的 token

5  计算效率对比

Jagged 的收益来自两个方面：消除 padding 浪费，以及注意力计算量随序列长度的二次方缩减。当序列长度差异大时，收益尤为显著。

设 $n$ 条序列长度为 $[l_1, l_2, ..., l_n]$，最大长度为 $L = \max(l_i)$：

$$\text{Padding 计算量} \propto n \cdot L^2 \qquad \text{Jagged 计算量} \propto \sum_{i=1}^n l_i^2$$
注意力计算是 $O(L^2)$ 的，序列长度对计算量影响是二次方级别
交互 · 计算量对比

拖动滑块改变序列长度，观察 Padding vs Jagged 计算量的差距

为什么二次方差距这么大：假设3条序列长度为 [2, 8, 2]，最大长度 8。Padding 计算量 ∝ 3×64=192；Jagged 计算量 ∝ 4+64+4=72，节省 62%。如果差距更极端，节省比例更高。

6  实现：cu_seqlens

Jagged Attention 的实现核心是维护一个累积序列长度数组（cumulative sequence lengths），告诉 kernel 每条子序列的边界在哪里。

$$\text{cu\_seqlens} = [0,\; l_1,\; l_1+l_2,\; l_1+l_2+l_3, \; \ldots]$$
FlashAttention varlen 接口中的 cu_seqlens_q / cu_seqlens_k

有了边界信息，CUDA kernel 就能为每个序列块独立计算注意力，不同块之间完全不相互影响，也不需要构造显式的大型掩码矩阵。这是 FlashAttention 的 flash_attn_varlen_func 接口背后的核心机制。

图示 · cu_seqlens 工作原理

cu_seqlens 数组标记每条子序列的起止位置，kernel 据此分配计算任务

与 Flash Attention 的关系：Flash Attention 的 varlen 版本（变长注意力）就是 Jagged Attention 的高效实现。它直接在 CUDA level 处理不规则序列，不构造完整掩码矩阵，内存和计算都是 $O(\sum l_i^2)$ 而非 $O(n \cdot L^2)$。

7  CUDA Kernel 底层：内循环如何跳过跨序列计算

仅有 cu_seqlens 数组还不够——关键在于 kernel 如何利用边界信息直接缩短内循环范围，而不是计算完再用掩码过滤。

标准 FlashAttention：扫描完整序列

对每个 query 块，内循环遍历整条拼接序列的所有 K/V token：

for kv_start in range(0, total_len, BLOCK_SIZE):
    scores += Q[q_start:q_end] @ K[kv_start:kv_end].T
    # ↑ 遍历所有 K/V，包括其他序列的（就算加了 block-diagonal mask，跨序列的 QK 乘法仍然被执行）
执行的 QK 乘法次数 ∝ (total_len)² = (Σlᵢ)²；其中属于同一序列的部分有意义，跨序列的部分虚耗了计算资源

Varlen FlashAttention：只扫描本序列

先通过 cu_seqlens 确定当前 query 属于哪条序列，然后内循环只访问该序列的 K/V：

seq_id    = find_seq(q_start, cu_seqlens)      # 二分查找
seq_start = cu_seqlens[seq_id]
seq_end   = cu_seqlens[seq_id + 1]

for kv_start in range(seq_start, seq_end, BLOCK_SIZE):
    scores += Q[q_start:q_end] @ K[kv_start:kv_end].T
    # ↑ 只遍历本序列的 K/V，跨序列 token 从不被访问
计算量 ∝ Σlᵢ²，跨序列的 QK 乘法根本不执行

线程块如何分配

标准版按总长度均匀切块，varlen 版按每条序列独立切块：

# 标准版：
num_blocks = ceil(total_len / BLOCK_M)    # 所有序列合并分块

# varlen 版：
num_blocks = Σᵢ ceil(lᵢ / BLOCK_M)       # 每条序列独立分块
每个线程块在启动时就知道自己属于哪条序列，计算完全不越界

内存布局为什么 cache 友好

打包后 K/V 在内存里是按序列顺序连续排列的。内循环访问 [seq_start, seq_end) 这段连续地址，没有随机跳跃，L2 cache 命中率高：

图示 · 内存布局与内循环范围

每个线程块（▼）只扫描本序列在内存中的连续区间，从不触碰其他序列的 K/V

总结：Jagged Attention 的效率不靠"计算完再 mask"，而是在 kernel 层面彻底不做跨序列的 QK 乘法。cu_seqlens 是边界表，让内循环的起止点从 [0, total) 收缩到 [seq_start, seq_end)，这才是计算量从 $(\sum l_i)^2$ 降到 $\sum l_i^2$ 的根本原因。
